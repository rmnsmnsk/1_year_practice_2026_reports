\section{Постановка задачи}

Работа выполняется в рамках учебного проекта кафедры системного программирования.

\textbf{Целью работы является} сравнительный анализ производительности двух подходов к хранению и обработке разреженных матриц: собственной реализации на языке C с использованием формата COO (Coordinate List) и эталонной реализации на языке F\# с использованием иерархической структуры QuadTree (библиотека \texttt{QTreeFSharp}\footnote{URL: \url{https://github.com/Lamagraph/QTreeFSharp} (дата обращения: май 2026)}).

Результаты работы необходимы для обоснования выбора архитектурных решений при разработке высокопроизводительных вычислительных систем. Для конечных пользователей (разработчиков численных методов, инженеров по оптимизации) это полезно пониманием компромиссов между простотой реализации и производительностью. В выполнении работы заинтересована кафедра системного программирования.

\section{Описание предлагаемого решения}

Сравнение проводилось между двумя подходами к хранению разреженных матриц:

\begin{itemize}
    \item \textbf{C (COO Format)}: собственная реализация на языке C, использующая формат (COO) с тремя плоскими массивами (индексы строк, индексы столбцов, значения). Управление памятью осуществляется вручную через \texttt{malloc}/\texttt{free}, аллокация производится единовременно при создании матрицы. Алгоритмы оптимизированы под последовательный доступ к памяти.

    \item \textbf{F\# (QuadTree)}: эталонная библиотека \texttt{QTreeFSharp}, использующая иерархическую структуру QuadTree. Операции реализованы рекурсивно, управление памятью автоматическое (Garbage Collector), что приводит к созданию множества временных объектов в процессе вычислений.
\end{itemize}

Реализация решения осуществлялась с использованием языка C (стандарт C11, компилятор GCC 13), языка F\# (.NET 8.0), системы сборки CMake для C-части и .NET SDK для F\#-части. Для автоматизации бенчмарков использовались скрипты на Python 3.

\section{Эксперименты}

\subsection*{Методика измерений}

\begin{itemize}
    \item \textbf{Наборы данных}: синтетические матрицы размеров $100{\times}100$, $500{\times}500$, $1000{\times}1000$, $2000{\times}2000$ с плотностью 5\%, 2\%, 1\%, 0.5\%; реальные матрицы из SuiteSparse Matrix Collection (\texttt{curtis54}, \texttt{cage4}, \texttt{lp\_afiro}).
    \item \textbf{Векторы}: синтетические, генерируются случайно с плотностью 10\%, размер соответствует количеству столбцов матрицы.
    \item \textbf{Инструменты замеров}:
    \begin{itemize}
        \item C: POSIX-таймер \texttt{gettimeofday()} с точностью до микросекунд, усреднение по 5 запускам.
        \item F\#: для малых размеров (10--20) --- библиотека \texttt{BenchmarkDotNet} для получения статистики аллокаций и учёта влияния GC; для больших размеров (100--2000) --- \texttt{System.Diagnostics.Stopwatch}, так как код завершается с ошибкой до начала итераций BDN.
    \end{itemize}
    \item \textbf{Лимиты}: таймаут 120 с для C, 3600 с для F\#.
    \item \textbf{Оформление}: все таблицы приведены к единому масштабу (секунды), точность унифицирована (6 знаков после запятой).
\end{itemize}

\subsection*{Проблема Stack Overflow в F\# реализации}

При запуске на размерах $\ge 50$ эталонная библиотека \texttt{QTreeFSharp} завершается с ошибкой \texttt{StackOverflowException}.

\textbf{Причина:} функция \texttt{Vector.traverse} (строка 314 в \texttt{Vector.fs}) использует \textbf{не-хвостовую рекурсию}:
\begin{verbatim}
let rec traverse coordinates pointer size =
    let left, lCoordinates = traverse coordinates pointer halfSize
    let right, rCoordinates = traverse lCoordinates (pointer+half) halfSize
    mkNode left right, rCoordinates
\end{verbatim}

Результаты комбинируются \textbf{после} возврата из рекурсивных вызовов, поэтому компилятор F\# не может применить оптимизацию хвостовой рекурсии (TCO). При размере $\ge 50$ глубина стека превышает стандартный лимит .NET ($\sim$8 МБ).

\textbf{Почему в других средах может работать:} возможно, используется иная версия .NET/JIT, Release-сборка с более агрессивными оптимизациями, или отличается структура входных данных (распределение ненулевых элементов влияет на глубину обхода QuadTree).

\textbf{Влияние на бенчмаркинг:} \texttt{BenchmarkDotNet} требует стабильного многократного выполнения метода для расчёта статистики (warmup + pilot + main iterations). Если код падает на этапе подготовки, BDN не доходит до фазы измерения и фиксирует ошибку. Поэтому для больших размеров использовался \texttt{Stopwatch}, который фиксирует время успешного одиночного запуска.

\subsection*{Выводы из экспериментов}

\begin{enumerate}
    \item C-реализация опережает F\# в \textbf{5--2000 раз} на идентичных данных в зависимости от операции и размера матрицы.
    \item Реализация на F\# создаёт тысячи временных объектов в куче (аллокации 62--403 КБ), что генерирует нагрузку на GC (Gen0: 10--65 на 1000 операций) и приводит к непредсказуемым паузам.
    \item На размерах $\ge 50$ эталонная библиотека завершается с \texttt{StackOverflowException} из-за не-хвостовой рекурсии в функции \texttt{Vector.traverse}, тогда как C-реализация стабильно работает до $2000{\times}2000$.
    \item Плоские форматы хранения (COO) обеспечивают предсказуемую линейную масштабируемость и отсутствие накладных расходов managed-среды.
    \item \texttt{BenchmarkDotNet} успешно применён для малых размеров, где код стабилен; для больших размеров использован \texttt{Stopwatch}, так как код не выдерживает протокол многократных запусков BDN.
\end{enumerate}

\section{Заключение}

В ходе выполнения работы получены следующие результаты:

\begin{itemize}
    \item Реализована собственная библиотека разреженной линейной алгебры на языке C в формате COO с операциями умножения матриц и матрицы на вектор.
    \item Проведён сравнительный бенчмаркинг с эталонной реализацией на F\# (QuadTree) на синтетических и реальных матрицах.
    \item Продемонстрировано преимущество плоских форматов хранения: ускорение в 5--2000 раз, отсутствие проблем с переполнением стека, предсказуемое потребление памяти.
    \item Интегрирован BenchmarkDotNet для профессионального анализа F\#-кода, выявлены архитектурные ограничения рекурсивного подхода.
    \item Исследована проблема Stack Overflow в эталонной библиотеке, даны рекомендации по диагностике различий в поведении кода в разных средах.
\end{itemize}
