\section{Введение}

Разреженные матрицы, где большинство элементов нулевые, возникают в задачах вычислительной математики, анализа графов и машинного обучения. Хранение таких матриц в полном виде неэффективно, поэтому разработаны специализированные форматы и библиотеки для работы с ними.

\section{Цель работы}

\text{Целью работы является} анализ компромиссов между двумя подходами к хранению и обработке разреженных матриц: императивной реализацией на языке C с форматом COO (Coordinate List) и функциональной реализацией на языке F\# с иерархической структурой QuadTree (библиотека \texttt{QTreeFSharp}).
\section{Обзор}

Разреженные матрицы могут храниться в различных форматах. Формат COO (Coordinate List) представляет матрицу тремя плоскими массивами. индексы строк, индексы столбцов и значения ненулевых элементов. Альтернативный подход представлен в готовой библиотеке \texttt{QTreeFSharp} --- подход, где используется иерархическая структура QuadTree.

\section{Описание предлагаемого решения}

Сравнение проводилось между двумя подходами к представлению разреженных матриц.

\begin{itemize}
    \item{C (COO Format)}. Реализация на языке C, использующая формат Coordinate List (COO) с тремя плоскими массивами (индексы строк, индексы столбцов, значения). Управление памятью осуществляется вручную через \texttt{malloc}/\texttt{free}, аллокация производится единовременно при создании матрицы.

    \item F\# (QuadTree). Использование эталонной библиотеки \texttt{QTreeFSharp} примененной без модификаций и скомпилированной под .NET 8.0.
\end{itemize}

\section{Эксперименты}

\subsection{Методика измерений}

\begin{itemize}
    \item \text{Были использованы} синтетические матрицы размеров $100{\times}100$, $500{\times}500$, $1000{\times}1000$, $2000{\times}2000$ с плотностью 5\%, 2\%, 1\%, 0.5\%; реальные матрицы из SuiteSparse Matrix Collection (\texttt{curtis54}, \texttt{cage4}, \texttt{lp\_afiro}).
    \item \text{Рассматривались}  синтетические векторы, которые генерируются случайно с плотностью 10\%, размер соответствует количеству столбцов матрицы.
    \item \text{Инструменты измерения}.
    \begin{itemize}
        \item C. POSIX-таймер \texttt{gettimeofday()} с точностью до микросекунд, усреднение по 5 запускам.
        \item F\#. для малых размеров (10--20) --- библиотека \texttt{BenchmarkDotNet} для получения статистики аллокаций и учёта влияния сборщика мусора; для больших размеров (100--2000) --- \texttt{System.Diagnostics.Stopwatch}, так как при многократных запусках код завершается с ошибкой до начала измерительных итераций \texttt{BenchmarkDotNet}.
    \end{itemize}
\end{itemize}

\subsection{Наблюдения при работе с F\# реализацией}

При запуске на матрицах с размерностью $\ge 50$ в среде выполнения (Ubuntu 24.04, .NET 8.0, Debug-сборка) библиотека \texttt{QTreeFSharp} завершается с ошибкой \texttt{StackOverflowException}.

\text{Возможная причина --- функция} \texttt{Vector.traverse} (строка 314 в \texttt{Vector.fs}) использует не-хвостовую рекурсию.
\begin{verbatim}
    let rec traverse coordinates pointer size =
    let left, lCoordinates = traverse coordinates pointer halfSize
    let right, rCoordinates = traverse lCoordinates (pointer+half) halfSize
    mkNode left right, rCoordinates
\end{verbatim}
Результаты комбинируются после возврата из рекурсивных вызовов, поэтому компилятор F\# не может применить оптимизацию хвостовой рекурсии. При увеличении глубины обхода дерева потребление стека растёт линейно. В других средах (иная версия .NET, Release-сборка, увеличенный лимит стека, другая структура входных данных) поведение может отличаться. В данной работе фиксируется наблюдаемое поведение в конкретной конфигурации.

\texttt{BenchmarkDotNet} требует стабильного многократного выполнения метода для расчёта статистики. При аварийном завершении на этапе подготовки измерения не проводятся. Поэтому для больших размеров использовался \texttt{Stopwatch}, фиксирующий время одиночного успешного запуска.

\subsection{Выводы по эксперементам}

\begin{itemize}
    \item На идентичных данных реализация на языке C показывает меньшее время выполнения операций по сравнению с использованием библиотеки на F\#. Разница варьируется в зависимости от операции, размера матрицы и структуры данных.
    \item При использовании \texttt{QTreeFSharp} наблюдаются значительные аллокации в куче (десятки и сотни килобайт на операцию), что создаёт нагрузку на сборщик мусора. В императивной реализации на C память выделяется единовременно и предсказуемо.
    \item При размерности матрицы $\ge 50$ наблюдается переполнение стека в \texttt{QTreeFSharp}, что ограничивает применимость этой библиотеки для больших задач без изменения конфигурации среды или модификации кода.
    \item Плоские форматы хранения (COO) в сочетании с императивной реализацией обеспечивают линейную масштабируемость и отсутствие накладных расходов, связанных с управляемой средой выполнения.
    \item \texttt{BenchmarkDotNet} успешно применён для анализа кода на малых размерах; для больших размеров использовался \texttt{Stopwatch}, так как код не выдерживает протокол многократных запусков, требуемый \texttt{BenchmarkDotNet}.
\end{itemize}

\section{Заключение}

В ходе выполнения работы получены следующие результаты.

\begin{itemize}
    \item Реализована библиотека разреженной линейной алгебры на языке C в формате COO с операциями умножения матриц и матрицы на вектор.
    \item Проведено сравнительное измерение производительности с использованием эталонной библиотеки на языке F\# (QuadTree) на синтетических и реальных матрицах.
    \item Продемонстрированы различные компромиссы подходов.   Императивная реализация на C обеспечивает высокую производительность, предсказуемое потребление памяти и линейную масштабируемость за счёт однократной аллокации и последовательного доступа к памяти; функциональная реализация на F\# демонстрирует компактность и выразительность кода, естественно отражает рекурсивную структуру алгоритма QuadTree, но порождает значительные накладные расходы на аллокации промежуточных объектов и ограничена глубиной рекурсии при больших размерах матриц.
    \item Интегрирована библиотека \texttt{BenchmarkDotNet} для детального анализа аллокаций и влияния сборщика мусора в F\#-коде.
    \item Исследовано поведение \texttt{QTreeFSharp} при увеличении размера входных данных. Подход на C предпочтителен для задач, критичных к производительности и объёму памяти; подход на F\# удобен для прототипирования, учебных демонстраций и задач с матрицами малой размерности, где выразительность кода важнее абсолютной скорости.
\end{itemize}
