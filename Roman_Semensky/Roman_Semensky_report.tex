\section{Постановка задачи}

Работа выполняется в рамках учебного проекта кафедры системного программирования.

\textbf{Целью работы является} сравнительное измерение производительности двух подходов к хранению и обработке разреженных матриц: реализации на языке C с использованием формата COO (Coordinate List) и использования эталонной библиотеки на языке F\# с иерархической структурой QuadTree (\texttt{QTreeFSharp}\footnote{URL: \url{https://github.com/Lamagraph/QTreeFSharp} (дата обращения: май 2026)}).

Результаты работы полезны для понимания компромиссов между императивной и функциональной реализациями при работе с разреженными данными. Для разработчиков численных методов это позволяет осознанно выбирать инструменты в зависимости от требований к производительности, читаемости кода и масштабируемости.

\section{Описание сравниваемых подходов}

Сравнение проводилось между двумя подходами к представлению разреженных матриц.

\begin{itemize}
    \item \textbf{C (COO Format)}: реализация на языке C, использующая формат Coordinate List (COO) с тремя плоскими массивами (индексы строк, индексы столбцов, значения). Управление памятью осуществляется вручную через \texttt{malloc}/\texttt{free}, аллокация производится единовременно при создании матрицы. Алгоритмы оптимизированы под последовательный доступ к памяти.

    \item \textbf{F\# (QuadTree)}: использование эталонной библиотеки \texttt{QTreeFSharp}.
\end{itemize}

Реализация на языке C осуществлялась с использованием стандарта C11 и компилятора GCC 13. Для измерений на стороне F\# использовалась библиотека \texttt{QTreeFSharp} без модификаций, скомпилированная под .NET 8.0. Для автоматизации измерений использовались скрипты на Python 3.

\section{Эксперименты}

\subsection*{Методика измерений}

\begin{itemize}
    \item \textbf{Наборы данных}: синтетические матрицы размеров $100{\times}100$, $500{\times}500$, $1000{\times}1000$, $2000{\times}2000$ с плотностью 5\%, 2\%, 1\%, 0.5\%; реальные матрицы из SuiteSparse Matrix Collection (\texttt{curtis54}, \texttt{cage4}, \texttt{lp\_afiro}).
    \item \textbf{Векторы}: синтетические, генерируются случайно с плотностью 10\%, размер соответствует количеству столбцов матрицы.
    \item \textbf{Инструменты измерения}:
    \begin{itemize}
        \item C: POSIX-таймер \texttt{gettimeofday()} с точностью до микросекунд, усреднение по 5 запускам.
        \item F\#: для малых размеров (10--20) --- библиотека \texttt{BenchmarkDotNet} для получения статистики аллокаций и учёта влияния сборщика мусора; для больших размеров (100--2000) --- \texttt{System.Diagnostics.Stopwatch}, так как при многократных запусках код завершается с ошибкой до начала измерительных итераций \texttt{BenchmarkDotNet}.
    \end{itemize}
    \item \textbf{Лимиты}: таймаут 120 с для C, 3600 с для F\#.
    \item \textbf{Оформление}: значения времени приведены к секундам, точность --- 3--4 значащих цифры в зависимости от порядка величины.
\end{itemize}

\subsection*{Наблюдения при работе с F\# реализацией}

При запуске на матрицах с размерностью $\ge 50$ в нашей среде выполнения (Ubuntu 24.04, .NET 8.0, Debug-сборка) библиотека \texttt{QTreeFSharp} завершается с ошибкой \texttt{StackOverflowException}.

\textbf{Возможная причина:} функция \texttt{Vector.traverse} (строка 314 в \texttt{Vector.fs}) использует не-хвостовую рекурсию:
\begin{verbatim}
let rec traverse coordinates pointer size =
    let left, lCoordinates = traverse coordinates pointer halfSize
    let right, rCoordinates = traverse lCoordinates (pointer+half) halfSize
    mkNode left right, rCoordinates
\end{verbatim}
Результаты комбинируются после возврата из рекурсивных вызовов, поэтому компилятор F\# не может применить оптимизацию хвостовой рекурсии. При увеличении глубины обхода дерева потребление стека растёт линейно.

\textbf{Примечание:} в других средах (иная версия .NET, Release-сборка, увеличенный лимит стека, другая структура входных данных) поведение может отличаться. В данной работе фиксируется наблюдаемое поведение в конкретной конфигурации.

\textbf{Влияние на измерения:} \texttt{BenchmarkDotNet} требует стабильного многократного выполнения метода для расчёта статистики. При аварийном завершении на этапе подготовки измерения не проводятся. Поэтому для больших размеров использовался \texttt{Stopwatch}, фиксирующий время одиночного успешного запуска.

\subsection*{Выводы из измерений}

\begin{enumerate}
    \item На идентичных данных реализация на языке C показывает меньшее время выполнения операций по сравнению с использованием библиотеки на F\#. Разница варьируется в зависимости от операции, размера матрицы и структуры данных.
    \item При использовании \texttt{QTreeFSharp} наблюдаются значительные аллокации в куче (десятки--сотни килобайт на операцию), что создаёт нагрузку на сборщик мусора. В императивной реализации на C память выделяется единовременно и предсказуемо.
    \item В нашей среде выполнения при размерности матрицы $\ge 50$ наблюдается переполнение стека в \texttt{QTreeFSharp}, что ограничивает применимость этой библиотеки для больших задач без изменения конфигурации среды или модификации кода.
    \item Плоские форматы хранения (COO) в сочетании с императивной реализацией обеспечивают линейную масштабируемость и отсутствие накладных расходов, связанных с управляемой средой выполнения.
    \item \texttt{BenchmarkDotNet} успешно применён для анализа кода на малых размерах; для больших размеров использовался \texttt{Stopwatch}, так как код не выдерживает протокол многократных запусков, требуемый \texttt{BenchmarkDotNet}.
\end{enumerate}

\section{Заключение}

В ходе выполнения работы получены следующие результаты.

\begin{itemize}
    \item Реализована библиотека разреженной линейной алгебры на языке C в формате COO с операциями умножения матриц и матрицы на вектор.
    \item Проведено сравнительное измерение производительности с использованием эталонной библиотеки на языке F\# (QuadTree) на синтетических и реальных матрицах.
    \item Продемонстрированы различные компромиссы подходов: императивная реализация на C обеспечивает высокую производительность и предсказуемое потребление памяти, тогда как функциональная реализация на F\# предоставляет выразительный интерфейс, но с накладными расходами на управление памятью и рекурсивные вызовы.
    \item Интегрирована библиотека \texttt{BenchmarkDotNet} для детального анализа аллокаций и влияния сборщика мусора в F\#-коде.
    \item Исследовано поведение \texttt{QTreeFSharp} при увеличении размера входных данных, сформулированы рекомендации по диагностике различий в поведении кода в разных средах выполнения.
\end{itemize}
